# agentchute v1.7.3

Three small fixes from the first live run of v1.7.2 across a five-lane pool (2026-10-13). Hotfix; no wire change.

**Upgrading.** Protocol v2.5, registration `v: 3` and hub wire version 1 are unchanged from v1.7.2, and so is the enrollment text (v36). Run `agentchute update` once and relaunch your lanes; nothing else to do.

## `doctor` no longer warns every lane about a codex daemon that cannot host it ([#239](https://github.com/agentchute/agentchute/pull/239))

On a host with several pools, `codex_daemon_env` printed a WARN on every lane of every pool as long as any managed `codex app-server` daemon from some other pool was alive, and its text claimed every codex session on the host ran under that daemon. Since v1.7.0, `serve` adds `--no-daemon` to a codex launch when the installed codex advertises the flag and the invocation is compatible; a child running with it has its own in-process app-server, so the shared daemon's inherited environment never reaches its hooks or shell commands (ordinary lease fencing still applies to its sends).

When a daemon was found and a lane id is given, the check now reads the lane's serve child from the process table the way `codex_memories` does. A codex child with `--no-daemon` as its own word (scanning stops at `--`) reports OK, with a message saying the daemon does not host this lane's hooks, and still lists the foreign daemon with its pool. A serve child that is not codex is skipped, because the daemon cannot host that lane's hooks. A codex child without the flag, a lane whose serve process cannot be found, or an unreadable or empty child list keeps the previous token/repo verdict, whose WARN and OK texts now limit their hosting claim to "codex sessions launched without --no-daemon". Daemon enumeration failing still warns, and no daemon at all is still OK, before any child inspection. Observed after the fix on the pool that found it, with a scratch build of the merged code: the codex lane reports OK and the four non-codex lanes (two Claude Code, grok, Muse Code) skip.

## `boot`'s inherited-mail note measures against this serve's start ([#238](https://github.com/agentchute/agentchute/pull/238))

`boot` printed "inbox contains mail from before this registration — a previous <id> may have existed" whenever an unread message was older than the registration's `last_seen`, which boot itself had just refreshed. On a wrapper whose session-start hook runs at the first cue (codex, Muse Code) ordinary mail already queued before that first boot triggered it, and both lanes reported the note as an anomaly on their first v1.7.2 turn.

The cutoff is now the lane's `serve.claim` `started_at`, which every serve launch or reclaim sets and heartbeats never move: mail stamped before this serve started gets an advisory note that a previous incarnation may have existed, now worded "from before this serve started". Without a readable local claim carrying a non-zero `started_at` there is no note; that covers a hand-run session that has no such claim, and remote SSH lanes, whose lease lives on the hub rather than in the local state directory (a lane running locally on the hub follows the ordinary path). The note is advisory and nothing branches on it.

## `.muse/` and `.agents/` are ignored in the agentchute repo itself ([#238](https://github.com/agentchute/agentchute/pull/238))

`hooks install --wrapper muse` writes `.muse/hooks.json` into the control repo, and `--wrapper agy` writes `.agents/hooks.json`; this repo's `.gitignore` now ignores both directories like `/.codex/` and `/.gemini/`. `init` has never written hook-directory ignores and still does not; this is the project's own ignore file, not a binary change.

## Known limitations

- The PreToolUse guard still denies a read-only command that merely names a hook config path while mail is claimed (three lanes hit it in the live test). The guard is best-effort text matching by design (§15); use a file-read tool instead of `cat` while latched.
