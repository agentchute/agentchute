# agentchute v1.6.2

No new capability. This release fixes how a working lane meets its mail: a message that landed mid-turn forced the recipient to end its turn just to read it, and a lane whose terminal never went quiet could wait forever for a wake that was already moot. Both came out of one afternoon of watching codex lanes under the coordinator, and both fixes were specified first and implemented second. Alongside them: the post-v1.6.1 UX wave, and one CI failure that was a real race in the hub client.

**Upgrading.** Protocol v2.5 and registration wire version `v: 3` are unchanged; the only registry surface is one additive client-side error code, `E_RESULT_UNKNOWN`. Enrollment prose moves to marker **v32** — run `agentchute update` (or `agentchute setup`) once per control repo so the wrapper files are re-stamped. The two runtime changes — the same-session re-check and wake retirement — take effect only when a lane is **relaunched** on the new binary; a lane still running an older binary continues to deny a second `check` while latched, which is a compatibility limitation, not the intended flow. Operators of codex 0.154 should set `[tui] whimsy = false` in `~/.codex/config.toml` and restart their codex lanes. A joined machine and its hub still need matching versions — upgrade the hub first, as always.

## A message that lands mid-turn no longer ends the turn

- **A lane may check again in the same working turn.** Once a lane had claimed mail, a second `check` in that session was denied twice over — by the guard's deny list and by `check`'s own self-denial — while every gate phase blocks on unread mail. So mail arriving mid-turn forced the lane to end its turn, get re-prompted by its Stop hook, and start over. `check` leaves the deny list and its self-denial is gone. Every check replays uncommitted residue as `REDELIVERED`, deliberately without a skip rule: a set latch is not proof that every claimed message was displayed. Latch lifetime is unchanged, `ack`/`turn-end`/`update`/`setup`/`clean --mailbox` and the pipeline substrings stay denied, and a compound that pairs `check` with any of them is still denied whole. No hub wire change ([#206](https://github.com/agentchute/agentchute/pull/206)).
- **The spec says so first.** AGENTCHUTE.md §6.3 (check claims and displays, and may run again on a new cue or an unread/malformed gate result), §8 (wake retirement) and §15 (the guard's deny list), AGENTS.md E8 (drain and act within the working turn; a blocked continue gate means another consume/act pass, not a mandatory turn boundary), the PLAYBOOKS bus-turn and gate-review steps, and the enrollment templates at marker v32 ([#205](https://github.com/agentchute/agentchute/pull/205)).

## A wake that could park forever

- **A waiting wake is retired when the inbox drains.** The runner's idle test needs two seconds of terminal silence before it injects a cue. codex 0.154 repaints its composer every 150 ms while idle (upstream [openai/codex#42842](https://github.com/openai/codex/issues/42842), `tui.whimsy`, default on), so on every codex lane the queued wake sat inside the wait for the lane's whole life — `pending_wake` true, `last_injection` never set — and was never retired even after the mail it was for had been read. A runner now holds at most one outstanding wake attempt per pending-mail period; a poll that actually observes an empty inbox retires it without a cue, and a retired attempt is also drained from the wake channel so it cannot block the next period's cue. Ownership is rechecked immediately before delivery and again at completion, so a stale attempt neither injects into nor clears state belonging to a newer period. A tick error is not an empty inbox, malformed inbox files still cue, remote lanes retire on the hub tick's result, and there is no timed forced submission and no Ctrl-C escalation. `runner.json` gains no field ([#207](https://github.com/agentchute/agentchute/pull/207)).
- **Operator note.** The stopgap for codex 0.154 is `[tui] whimsy = false` plus a lane restart; measured on an idle pane it takes the repaint rate from ~6.6 frames a second to zero. `tui.animations = false` also works but freezes the Working timer.

## A CI failure that was a real race

- **The hub client classifies a deadline it can no longer set as a lost channel.** `OpenOneShotTransport` and the one-shot request path each set a deadline, write, set the read deadline, read. Write and read failures were classified; the deadline-set calls around them returned the raw transport error, and once the far end has closed that error is an unclassified `io: read/write on closed pipe`. It surfaced as an intermittent failure of one hub-client test on main and on two PRs (36 failures in 2,000 race-detector runs locally). All four sites now report `E_CHANNEL_LOST` with the same stage as their neighbours; `transmitted` and the `E_RESULT_UNKNOWN` rule are untouched ([#208](https://github.com/agentchute/agentchute/pull/208)).

## The post-v1.6.1 UX wave

- **Joining a hub no longer invents your shell profiles.** On a fresh account `hub join` created `~/.zshrc` and `~/.profile` when neither existed. Profiles that exist are still updated; absent ones are left absent and the operator is told exactly what to add, with `agentchute setup --profile <path>` to name one (naming it is the consent that was missing, so that path still creates it) and `setup --no-profile` to skip the step ([#204](https://github.com/agentchute/agentchute/pull/204), closes [#177](https://github.com/agentchute/agentchute/issues/177)).
- **An incomplete join no longer exits 0.** A join that printed "Run this ON THE HUB…" and stopped returned success, so a script checking the exit status believed the machine was fully joined while authorization was still pending. It now exits 2 — the code this CLI reserves for a verdict rather than a command failure — because the local half did succeed and re-running after authorizing is the intended next step ([#204](https://github.com/agentchute/agentchute/pull/204), closes [#178](https://github.com/agentchute/agentchute/issues/178)).
- **A drop after the hub already streamed output says so.** When the hub commits and streams its work and only the terminal frame is lost, the client used to report a plain channel loss — advice that, followed, re-delivers what was just shown. That outcome is now `E_RESULT_UNKNOWN`: everything printed did happen, the hub may have committed, check state before re-running. A drop with nothing streamed keeps its ordinary classification, where "nothing happened, re-run" is right ([#204](https://github.com/agentchute/agentchute/pull/204), closes [#171](https://github.com/agentchute/agentchute/issues/171)).

## Deliberately not in this release

The lifecycle-signal and structured-delivery half of the same decision (an idle signal from hooks; `codex queue` instead of composer injection) stays a requirements list until its probes run; the idle heuristic is unchanged, and a PTY write still only proves that bytes were written. A re-check re-prints residue every time — deduplicating that output would need per-message display bookkeeping and was rejected for now in favour of never skipping a message.
